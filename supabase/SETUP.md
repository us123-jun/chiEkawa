## Supabase 대시보드에서 한 번 실행

1. SQL Editor에서 `schema.sql` 전체를 실행합니다. 계정별 저장 테이블, RLS 정책, 저장 충돌을 감지하는 RPC를 생성합니다. 이 저장소는 관리자 인증정보를 포함하지 않으며, 배포만으로 SQL이 실행되지는 않습니다.
2. Authentication → Providers에서 Email을 활성화합니다. 기본 이메일 인증을 유지합니다.
3. Authentication → URL Configuration에서 Site URL과 Redirect URLs에 `https://us123-jun.github.io/chiEkawa/`를 등록합니다. 인증/비밀번호 재설정 메일에서 이 주소로 돌아옵니다. 로컬 테스트 시에는 해당 로컬 HTTP 주소도 별도로 허용합니다.
4. 테스트용 이메일로 가입 → 이메일 인증 → 로그인 → 밥 주기 → 로그아웃 → 재로그인 후 기록을 확인합니다. 다른 계정에서도 동일 검증을 하여 기록이 섞이지 않는지 확인합니다. 다른 기기에서도 같은 계정으로 확인합니다.

계정 데이터베이스 설정은 실제 Supabase 프로젝트에서 실행·확인해야 합니다. 로컬 모의 응답 검사는 실제 인증 메일 발송, 토큰 정책 또는 RLS의 실행 검증을 대신하지 않습니다.

## 저장 동작

손님 저장 키 `chiekawa-little-day-v1`은 유지하며 계정은 사용자 UUID별 로컬 키에 저장합니다. 계정에 서버 기록이 없을 때만 손님 기록 가져오기/새로 시작하기를 선택합니다. 기존 계정 기록은 서버에서 불러옵니다.

로컬 저장은 즉시, 서버 저장은 최대 15초 간격 및 화면을 떠날 때/온라인으로 돌아올 때 수행합니다. 로그아웃 시 먼저 서버 저장을 시도합니다. 네트워크 오류 시 계정별 로컬 기록과 미전송 표시를 유지합니다. 다른 기기의 수정과 충돌하면 자동 덮어쓰기를 멈추고, 사용자가 서버 기록을 불러올 때 로컬 기록을 별도 백업합니다. 로컬 저장을 차단한 브라우저/다른 기기에서는 미전송 기록이 복구되지 않을 수 있습니다.

15초 이내의 갑작스러운 기기 종료는 마지막 서버 저장 이후 기록이 다른 기기에 반영되지 않을 수 있습니다. 오프라인 동시 플레이를 자동 병합하지 않습니다.

## 개발 환경 네트워크

이 프로젝트의 HTTPS 호스트 `mhdqsjyypvppvmsosyts.supabase.co` 접근이 필요합니다. 환경 설정 초안 저장만으로 실행 중인 네트워크 정책은 바뀌지 않습니다. 이 설정은 클라우드 개발 도구의 접근을 위한 것이며 실제 사용자 브라우저의 연결 설정과는 별개입니다.

## 보안 범위

RLS는 사용자별 읽기/쓰기 권한을 분리합니다. 게임 수치는 클라이언트에서 계산하므로 사용자가 자기 기록을 수정하는 부정행위까지 방지하지는 않습니다. 경쟁/순위 기능을 추가한다면 서버에서 보상을 검증해야 합니다.

## 회귀 검사

- `cd tests && npm ci && npm run test:rls`: PostgreSQL 엔진(PGlite)에서 SQL 적용·RLS·저장 버전 충돌 검증. Supabase의 auth.users/auth.uid 환경을 테스트용으로 모사합니다.
- Python Playwright와 Chromium이 설치된 환경에서 `python tests/auth-flow.py`: 모의 Supabase 응답을 통한 로그인 UI·기록 분리·오프라인 재시도·저장 충돌 검사. 브라우저 실행 파일은 `/usr/bin/chromium`을 사용합니다.
